# Qloo integration contract and evidence

Reviewed October 24, 2026. Main documentation requests returned HTTP 403. The implementation therefore uses Qloo's [official public documentation mirror](https://github.com/qloo/docs-public) pinned to revision **`d4a0eb978518f7fb404993d1509d11b21239ada6`**, plus request/envelope conventions inspected in Qloo's own published **`@qloo/qloo-harness@0.1.26`** package. This is documentation review, **not** a live Qloo API test.

## Implemented requests

| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication                 | Server `X-Api-Key` header, never URL or browser                                                                                                                                                                                | [Onboarding](https://github.com/qloo/docs-public/blob/d4a0eb978518f7fb404993d1509d11b21239ada6/reference/api-onboarding.md)                                                                                                                                          |
| Named artist/film lookup       | `GET /search?query=...&types=urn:entity:artist` (or `urn:entity:movie`) `&take=5`                                                                                                                                              | [Search](https://github.com/qloo/docs-public/blob/d4a0eb978518f7fb404993d1509d11b21239ada6/reference/get-search.md)                                                                                                                                                  |
| Genre/concept lookup           | `GET /v2/tags?filter.query=...&take=5`                                                                                                                                                                                         | [Tags](https://github.com/qloo/docs-public/blob/d4a0eb978518f7fb404993d1509d11b21239ada6/reference/get-tags.md)                                                                                                                                                      |
| Cultural place discovery       | `GET /v2/insights` with `filter.type=urn:entity:place`, comma-separated `signal.interests.entities` and/or `signal.interests.tags`, `filter.location=POINT(longitude latitude)`, `filter.location.radius` in meters, `take=12` | [Deep dive](https://github.com/qloo/docs-public/blob/d4a0eb978518f7fb404993d1509d11b21239ada6/reference/insights-api-deep-dive.md), [parameter reference](https://github.com/qloo/docs-public/blob/d4a0eb978518f7fb404993d1509d11b21239ada6/reference/parameters.md) |

No legacy `/recs` or `/recommendations`, undocumented search action, made-up entity ID, guessed tag URN, or invented date/availability parameter is sent. Area circles are app-defined; the API's point uses longitude first. Returned points are checked again server-side, so a location parameter being ignored does not certify out-of-area records.

The default origin is **`https://api.qloo.com`**, confirmed in the official recipes and harness. Its onboarding examples also reference staging. This does **not** establish which host a particular event key may access. Set `QLOO_BASE_URL` only to the exact Qloo API origin provided with your credential. Alternate Qloo HTTPS API origins are configurable; errors do not trigger host/key fallback. No third-party host can receive the key.

## Response validation

The minimal parser recognizes the provider's result-array and nested `results.entities` / `results.tags` envelopes, including the maintained harness's result-array convention. Explicit `success:false`, missing collections and unreadable payloads are errors. Search's documented HTTP 404 becomes no matches; other endpoint 404s remain failures.

- Entities require nonempty `name`, a UUID-shaped `entity_id`, and a compatible `type`/`subtype`.
- Tags require `id` beginning `urn:tag:`, a nonempty `name`, and an optional `type` label.
- Places require `location.lat` and `location.lon` and place type. Only supplied description, address, websites, price-level and tag fields are exposed. Missing descriptions stay missing. Invalid/absent coordinates, duplicates, wrong types and out-of-area places are discarded and counted.
- Optional website links must be HTTPS without embedded credentials. No provider image asset is copied or embedded.

The client is deliberately minimal and fail-closed. A schema difference in a real key's response may require an adapter change after checking actual authorized output. It must not be repaired by guessing place coordinates or substituting fixture data.

## Documentation caveats and limits

The mirror's file named `openapi-schema.json` is an OpenAPI meta-schema, not an operation document containing Qloo `paths`; it was not treated as evidence of unlisted request/response fields. The endpoint guides and maintained harness were inspected instead. The event-specific guide and numeric account quota could not be fully read in this environment. The [official hackathon kit's access notes](https://github.com/qloo/qloo-hackathon-kit/blob/main/docs/API_ACCESS.md) direct participants to their issued quota, rate, expiry and supported access surface; confirm those in your own access instructions before live use. No numeric provider quota is claimed here.

Local safeguards: 12-second Qloo timeout, no automatic retries, four taste terms, two simultaneous lookups, one Insights query, 30 outbound Qloo requests/minute per instance, and bounded short-lived in-memory caching. These safeguards do not override account terms or limits. The issuer's access conditions take precedence; if a credential is restricted to a harness/gateway surface, obtain authorization for REST usage or adapt this boundary to that approved surface before running live.

Gemini uses documented [`generateContent`](https://ai.google.dev/api/generate-content) with a JSON Schema; schema validation and explicit price-tier detection are applied server-side. It never receives the Qloo API key or Qloo place data, and it does not invent the itinerary.
